Self-Hosted RAG in Production: What the Tutorials Skip

Most “self hosted RAG with Ollama” tutorials end at the same place: a notebook that answers questions over one PDF, running on localhost, with no login page. That is a demo. A self hosted RAG deployment — the thing a team actually uses on Tuesday morning — needs user accounts, permissions, a config that survives a restart, an upgrade path for the models, and answers to “port already in use” at 9 a.m. This post is the checklist I worked through while turning my own RAG prototype into a deployable system (Self-Hosted RAG, the app I built and ship as complete source). It is organized around the five gaps between demo and deployment, so you can audit your own setup — whichever stack you run.

Gap 1: Authentication and multi-user are not optional

A tutorial can ignore auth because it has one user: you. The moment a second person touches the system, you need accounts. The moment you have accounts, you need an admin who manages them. In my app this is a dedicated auth.py module plus an admin dashboard for user management and system analytics — not because it is glamorous, but because “who can log in” is the first production question any team asks.

Two rules from shipping this:

  1. Force the password change on first boot. My installer creates an admin / admin123 account and the README tells you to change it immediately. If you are building your own, make the app refuse team mode until the default password is gone. Password complexity rules belong in config, not in hope.
  2. Separate deployment modes. config.json has a deployment section with personal (single user) and team (multi-user) values. A personal install should not carry team surface area, and a team install should not run without accounts. One switch, checked at startup.

Gap 2: Permissions are per knowledge base, not global

Multi-user without permissions is worse than single-user: anyone can upload anything into the collection everyone queries. The unit of access control that matches how teams work is the knowledge base — “the HR collection is read-only for most, upload for two people” is a real requirement; “everyone is an admin” is not an answer.

Each knowledge base in my config.json carries its own flags:

{
  "id": "your_topic",
  "name": "Your Topic",
  "description": "Documents for your topic",
  "chroma_db_path": "./chroma_db_store/your_topic",
  "chroma_collection_name": "your_topic_collection",
  "document_paths": ["./knowledge_bases/your_topic"],
  "enabled": true,
  "color": "#007bff",
  "type": "team",
  "allow_uploads": true,
  "read_only": false
}

read_only, allow_uploads, and enabled per collection — that is the whole model, and it covers most team situations without a permissions database. If you are designing your own, resist going finer than this at first; per-document ACLs inside a local RAG app are where weekend projects go to die.

Related: before confidential documents go into any shared collection, strip the identifiers you do not want indexed. I treat offline PII redaction as a pre-ingest step, not an afterthought — see also my guide to redacting PDFs without Adobe Pro.

Gap 3: Retrieval settings decide self hosted RAG quality

Chunk size and retrieval settings decide answer quality more than the LLM does. In this app they are fields in the rag section of config.json, next to the Ollama URL and model names — which means they are tunable without touching code, and reviewable in one place.

The practice I recommend: change one variable at a time, keep a small set of questions you ask after every change, and compare the retrieved passages — not just the generated answers. Retrieval is usually where quality is lost. I deliberately do not publish “optimal” chunk numbers here; they depend on your documents, and anyone who gives you a universal constant is guessing.

Gap 4: Size the models to the box, and plan the upgrade

The default pairing in my install is compact and runs on modest hardware: qwen3:4b for generation, qwen3-embedding:0.6b for embeddings — both pulled automatically by the installer. When the machine is stronger (20 GB+ VRAM, or 24 GB+ unified memory on Apple Silicon), the README’s upgrade path is deliberately boring:

ollama pull qwen3:30b

then one line in config.json:

"llm_model": "qwen3:30b"

No reinstall, no migration, no re-index of the vector store — embeddings and generation are separately configured, so upgrading the chat model does not invalidate the collection you already built. If you switch embedding models, that is the change that forces a re-index; plan for it. Model references: Qwen3 and Qwen3 Embedding on Ollama.

Gap 5: Ops is a first-class feature

The unglamorous list that decides whether people keep using the system:

  • Restart story. A restart_app.sh script and a “knowledge base not showing → restart after config edits” note in the README. Config changes should have one documented, boring path to take effect.
  • Port conflicts. Port lives in config, not in code. “Already in use” is the most common support question for any local web app; make the answer a one-line edit.
  • Dependency clarity. requirements.txt plus a venv the run scripts activate. The README’s troubleshooting table (Ollama not running, ImportError, port, missing KB) maps to the four failures you will actually hit.
  • Readable stack. Flask, ChromaDB, LangChain, Ollama — standard, inspectable components. When you self-host, “trust me” is not an architecture; you should be able to read every line that touches your documents.

Should you build this or ship it?

If the checklist above reads like your next six weekends, that is the honest signal. The demo is 10% of the work — the other 90% is everything above. Build it yourself if the building is the point; take the shortcut if the answering is the point. Either way, hold your deployment to this checklist.

FAQ

How is this different from the beginner tutorials?

Tutorials cover ingest-to-answer on one PDF in a notebook. This post (and the app) cover the deployment layer: auth, per-KB permissions, config, model upgrades, ops. Both are legitimate; only one survives contact with a team.

Can multiple people use a self hosted RAG at once?

Yes — with accounts. The app ships multi-user with an admin dashboard and per-knowledge-base read/upload permissions, plus a single-user personal mode if you do not need any of it.

Which document formats work?

PDF, DOCX, TXT, MD, and CSV.

What hardware do I need?

The default Qwen models run on modest hardware via Ollama; the larger qwen3:30b path targets 20 GB+ VRAM or 24 GB+ unified memory. You need Python 3.10+.

Do my documents leave the server?

No. Parsing, embedding, vector search, and generation all run locally — there is no cloud AI API call anywhere in the pipeline.
