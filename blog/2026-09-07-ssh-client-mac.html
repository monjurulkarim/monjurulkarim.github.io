SSH Client on Mac: Keys, Config, and Tunnels (2026)

Every Mac ships with a complete SSH client. Before you download anything: open Terminal, type ssh, and you’re holding the same open-source suite (OpenSSH) that most of the world’s servers run. The catch is that the built-in SSH client on a Mac is invisible until someone shows you the workflow around it — keys, host aliases, file transfers, and the tunnel tricks that turn a remote machine into a local one.

This guide covers that workflow end to end. It’s written for people who SSH occasionally and suspect they’re doing it the hard way — and at the end, it covers the one job where the terminal genuinely runs out of patience.

The client you already have

Open Terminal and check what you’re working with:

ssh -V

A basic connection is one line:

ssh user@server.example.com

The first time you connect to a host, the client prints the host’s fingerprint and asks whether to trust it. This is your protection against impostor servers — the fingerprint is remembered in ~/.ssh/known_hosts, and you’ll only be warned again if it changes unexpectedly. Type yes deliberately, not reflexively.

That’s a complete SSH client. Everything below makes it fast, safe, and mostly automatic.

Step one: set up keys (once, and never type that password again)

Password logins work, but keys are better in every way: faster to use, immune to simple guessing attacks, and required by many servers anyway.

Generate one:

ssh-keygen -t ed25519 -C "you@your-mac"

Accept the default location (~/.ssh/id_ed25519). The passphrase is optional — set one, because a key without a passphrase is as sensitive as a password written on a laptop lid.

Copy the public half to any server you log into:

ssh-copy-id user@server.example.com

(If your macOS lacks ssh-copy-id, the manual one-liner does the same job: cat ~/.ssh/id_ed25519.pub | ssh user@host "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys".)

Now add the passphrase to the macOS Keychain so you type it once, ever:

ssh-add --apple-use-keychain

The file that makes SSH pleasant: ~/.ssh/config

Typing ssh karim@128.95.204.218 -i ~/.ssh/some_key every time is how people learn to hate the terminal. The client reads a config file that turns any server into a two-letter alias:

Host gpu
    HostName 128.95.204.218
    User karim
    IdentityFile ~/.ssh/id_ed25519
    ServerAliveInterval 60

Host *
    AddKeysToAgent yes
    UseKeychain yes

With that in ~/.ssh/config, ssh gpu connects with the right user, key, and keep-alive. Every SSH tool on the system honors these aliases — scp, rsync, Git remotes, port forwards. The full option list is in the ssh_config manual (short version: almost any flag you’d type on the command line can be pinned per-host here).

ServerAliveInterval is the quiet hero: it keeps long sessions from freezing when a NAT table forgets you mid-afternoon.

Copying files without thinking about it

Three tools, in order of how much they forgive:

# one file, over SSH
scp report.pdf gpu:~/papers/

# a directory tree, efficiently (resumes, skips unchanged files)
rsync -avz ~/datasets/ gpu:~/datasets/

scp is the quick grab. sftp gives you an interactive session for browsing. But rsync is the one worth learning: it compares source and destination, transfers only differences, and can resume an interrupted multi-gigabyte copy — which matters the first time your laptop sleeps halfway through moving data to a lab server.

SSH tunnels: port forwarding in one line

The most under-used feature of any SSH client. A tunnel takes a service running on (or behind) a remote server and makes it appear on your own machine — no firewall ports opened, nothing exposed publicly.

The common case — a web dashboard that only listens on the server’s localhost:

ssh -L 8080:localhost:80 user@server.example.com

While that session is open, http://localhost:8080 on your Mac is tunneled to port 80 as the server sees it. This is the standard trick for admin panels, Jupyter servers, and database UIs you refuse to expose to the internet. (-R runs the same wire in reverse — useful for showing a colleague your local dev server. -D 1080 builds a simple SOCKS proxy, which survives on expert resumes as “the ssh SOCKS trick”.)

When a terminal tunnel isn’t enough

Tunnels have one honest weakness on a laptop: they die when your Mac sleeps, and they don’t come back on their own. For a one-off look at a dashboard that’s fine. For tunnels you want running all day — one to the lab server, one to a self-hosted app, one to a NAS — the terminal becomes a babysitting job: reconnect after every wake, remember which forward was which, check what’s still alive.

So which SSH client should you use on a Mac?

The honest answer: the built-in one, configured well, covers most people. Name-brand alternatives earn their place in specific cases — terminal multiplexers with profiles and split panes (iTerm2 is the long-respected name), or cross-platform SSH managers with synced host lists (Termius is the common one). Try them after the config file, not instead of it: every one of them reads ~/.ssh/config anyway.

FAQ

Is there an SSH client built into macOS?

Yes — OpenSSH is included with every Mac, in Terminal. No install needed: ssh user@host works on a fresh machine, and ssh -V shows the version.

How do I create SSH keys on a Mac?

ssh-keygen -t ed25519 -C "you@your-mac", accept the default path, set a passphrase, then ssh-copy-id user@server to install the public key on servers you use. Store the passphrase in the Keychain with ssh-add --apple-use-keychain.

Does a Mac have the SSH server too, or just the client?

Both. The client is always on; the server (sshd) is off until you enable it under System Settings → Sharing → Remote Login (the pane moves between macOS releases — search “Sharing” in System Settings). Turn it on to let other machines SSH into this Mac.

How do I keep an SSH tunnel alive when my Mac sleeps?

For sessions, ServerAliveInterval 60 in your config prevents idle disconnects. For tunnels, the terminal itself has no reconnect-on-wake — which is why the tunnel app I built makes auto-reconnect its headline feature. Alternatives: autossh (free, terminal) or closing and re-running your -L command after each wake.
